# File sharing: build contract

The agreed design for file sharing on top of shared folders
(`internal/shares`, see `docs/shares.md`). Several parts are built in
parallel; this fixes the names, formats and operations they share. Say so in
your summary if you need to diverge.

Cade's decisions this implements (2026-10-26):

- Protocols: SMB (Windows/Mac), Time Machine, NFS (by machine address),
  SFTP and WebDAV.
- Simple per-folder permissions (the access rules shared folders already
  store: domain users and groups, Everyone; read / write / none), plus an
  optional guest share.
- Safety nets: snapshots shown as Windows Previous Versions, a recycle bin.
- Home folder per user; Media and Backups starter folders already exist.
- Remote access over the NetBird VPN plus web share links (the links work
  on the LAN now; reaching them from outside comes with the reverse proxy).
- A File Manager app in the web desktop, built together with file sharing.

## 0. What's already there

- Shared folders are datasets `<pool>/shares/<id>` (acltype=posixacl,
  xattr=sa, aclinherit=passthrough), settings in `org.hardyos:*` properties.
  `Share.Access` rules, `Recycle`, `Guest`, quota; apps get POSIX ACL entries
  for their own UIDs (30000-30999) through the no-follow walker in
  `shares/acltree_linux.go`.
- New in this contract: `Share.Services` (`org.hardyos:services`, JSON; see
  `shares/services.go` and the `ShareServices` OpenAPI schema): SMB on/off,
  Time Machine (+ max size), Previous Versions, NFS clients, snapshot
  retention (hourly/daily/weekly/monthly counts). New folders default to SMB
  on with Previous Versions, NFS off, 24/14/8/6 snapshots.
- This NAS may run the domain controller (Samba AD DC in its own network
  namespace `hardyos-dc` with its own LAN address). The NAS resolves the
  domain through it already (decision 49).

## 1. SMB file server (part A)

- The **host** runs a separate Samba (`smbd`, `winbindd`, `nmbd` off) as a
  **domain member** — never the DC's Samba (Samba doesn't support a DC as a
  general file server). Config is generated by hardyd-priv into
  `/etc/samba/smb.conf` (the DC uses its own config in its data dir and its
  own `/run/samba`, so they don't collide). Debian's `smbd`/`winbind` units
  are used (the image currently masks them: unmask them and keep them
  disabled until joined).
- Joining: `files.join {adminPassword}` (password via the existing job
  secret box; never on a command line — `net ads join` reads `PASSWD` from
  the environment or stdin). When this NAS's own DC is provisioned or a DC
  joins, the provision/join job joins the file server too with the same
  password. Otherwise Control Panel > File Services offers "Join the
  domain" (domain name + admin password; the domain must be reachable).
  `files.leave` (confirm). Host `/etc/krb5.conf` is written for the realm.
- ID mapping: `idmap config * : backend = tdb, range = 3000-7999`;
  `idmap config <NETBIOS> : backend = rid, range = 100000-999999`. So
  domain users and groups have stable Linux IDs on every HardyOS server,
  clear of local users (1000-2999), app UIDs (30000-30999) and NFS UIDs
  (31000-31999). `winbind use default domain = no`; names are
  `HOME\alice` (`winbind separator = \`). NSS `passwd/group: files winbind`.
- Shares: one `[<Name>]` section per shared folder with `services.smb.enabled`
  and mounted; `path` = mountpoint; `vfs objects = acl_xattr` (+ `recycle`,
  `shadow_copy2`, `fruit streams_xattr` as needed); `inherit acls = yes`;
  `map acl inherit = yes`; `access based share enum = yes`.
  Access rules -> `valid users` / `read list` / `write list` / `invalid users`
  (none) and the matching POSIX ACL entries on the share root (access and
  default, via the same fd walker as app grants, background for big trees).
  Everyone = `HOME\Domain Users`. Guest (`guest ok = yes`, guests read-only,
  mapped to `nobody`) only when the folder's guest flag is on.
- Recycle bin: `vfs_recycle` into `.recycle/<netbios>.%U` (decision 106; hidden, `veto files`
  excludes nothing else), keeping folder tree and versions; files older than
  30 days are removed daily by hardyd-priv.
- Previous Versions: `shadow_copy2` with `shadow:snapdir = .zfs/snapshot`,
  `shadow:snapprefix = ^hardyos-auto-(hourly|daily|weekly|monthly)$`,
  `shadow:delimiter = _`, `shadow:format = _%Y-%m-%d-%H%M`,
  `shadow:localtime = no` — matching the snapshot names in section 2.
- Time Machine: `fruit:time machine = yes` (+ `fruit:time machine max size`),
  `vfs objects = catia fruit streams_xattr acl_xattr`, global
  `fruit:metadata = stream`, `fruit:model = MacSamba`; Avahi advertises
  `_smb._tcp` and `_adisk._tcp` (package `avahi-daemon`, service file
  generated by hardyd-priv).
- Home folders: dataset `<pool>/homes` (chosen pool, setting in File
  Services), one child dataset `<pool>/homes/<netbios>.<user>` (lowercase)
  per domain user, created by hardyd-priv for every enabled user (on enable
  and every 10 min), owner = the user, mode 0700, default quota setting.
  SMB `[homes]` with `path = <mount>/<netbios>.%U` style mapping (use a
  per-user `include` or `root preexec`-free approach — no scripts run as
  root on connect). Home folders are not shared folders (no access rules)
  but show in the File Manager as "Home".
- Settings and status: root ops `files.status`, `files.join`, `files.leave`,
  `files.settings {smbEnabled, homes: {enabled, pool, quotaBytes}}`,
  `files.apply` (regenerate config and reload; called by the shares ops after
  every change and by the watcher). API `GET /files`, `POST /files/join`
  (job), `POST /files/leave` (job, confirm), `PATCH /files/settings` (job).
  Web: Control Panel > **File Services** (status, join, SMB on/off, homes,
  how to connect from Windows/Mac/Linux with the server's name), and the
  SMB + Time Machine section of the shared folder dialog.

## 2. Snapshots and NFS (part B)

- Automatic snapshots per shared folder from `services.snapshots`, taken by
  a scheduler inside hardyd-priv (hourly at :00, daily 00:00, weekly Monday
  00:00, monthly 1st 00:00, UTC), named
  `<dataset>@hardyos-auto-<kind>_<YYYY-MM-DD-HHMM>` (UTC), pruned per kind to
  its count. Never touches other snapshots (manual ones, app snapshots).
  Missed runs (server off) are not back-filled except the newest of each kind.
- Manual snapshot / list / delete (confirm) / restore a file or folder from a
  snapshot (copy back next to the original, never a whole-dataset rollback
  from the UI). Root ops `snapshots.list {share}`, `snapshots.create
  {share, name}`, `snapshots.delete {share, snapshot, confirm}`. API under
  `/shares/{id}/snapshots`. Restoring single files is done by the File
  Manager (part C) reading `.zfs/snapshot/<name>/...` read-only.
- NFS: `nfs-kernel-server`, exports generated into
  `/etc/exports.d/hardyos.exports` + `exportfs -ra`. Every NFS client of a
  folder is squashed to one NFS identity per folder (`all_squash,
  anonuid=<uid>, anongid=<uid>` with a UID from 31000-31999 allocated per
  folder and stored in `org.hardyos:services`'s sibling property
  `org.hardyos:nfs-uid`), granted on disk like an app grant (read -> r-X,
  write -> rwX). So NFS clients can never act as a domain user or root.
  `sec=sys`, `no_subtree_check`, `rw`/`ro` per client rule, NFSv3 and v4.
  The shared folder dialog's NFS section shows the mount command.

## 3. File Manager backend (part C)

Files are read and written **as the person**, never as root on their behalf:

- A root op family `files.*` runs each operation in a short-lived child of
  hardyd-priv that has dropped to the person's Linux identity (domain users:
  their winbind uid, gids from `getgrouplist`; Linux `setgroups`,
  `setresgid`, `setresuid`, `PR_SET_NO_NEW_PRIVS`). HardyOS local admins
  (not domain accounts) act as a dedicated `hardyos-files` system user that
  is given read/write on every shared folder through the ACL walker (like an
  app grant, UID 29999) — never as root.
- Paths are resolved with `openat2(RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS |
  RESOLVE_NO_MAGICLINKS)` from the share root's fd, so nothing can escape a
  shared folder or follow a link. Hidden: `.recycle`, `.zfs` (except the
  snapshots view), `.hardyos*`.
- Operations: list, stat, mkdir, rename/move (within and across shares),
  copy, delete (to the recycle bin when the folder has one), download and
  upload (the child opens the file and passes the **file descriptor** back
  over the unix socket with SCM_RIGHTS; hardyd streams it — no file content
  goes through JSON), list snapshots of a path and open a file from a
  snapshot (read-only), restore from a snapshot (copy back with a
  "(restored <date>)" suffix if the name exists).
- hardyd: package `internal/files` exposes
  ```go
  type Who struct{ Principal string; Admin bool; Local bool } // from auth.Identity
  type Access interface {
      List(ctx, who Who, share, path string) ([]Entry, error)
      Stat(ctx, who Who, share, path string) (*Entry, error)
      Open(ctx, who Who, share, path string) (*os.File, *Entry, error)   // read
      Create(ctx, who Who, share, path string, overwrite bool) (*os.File, error)
      Mkdir / Rename / Copy / Delete / Snapshots / OpenSnapshot / Restore ...
  }
  ```
  (exact names in `daemon/internal/files/files.go`), and the API
  `/files/shares` (folders the person can see, plus Home),
  `/files/list?share=&path=`, `/files/download`, `/files/upload` (streamed,
  resumable in chunks for large files), `/files/mkdir`, `/files/rename`,
  `/files/copy`, `/files/delete`, `/files/snapshots`, `/files/restore`.
  Copies/moves/deletes of more than a handful of items run as jobs with
  progress. Audit: deletes, restores, uploads (name, size) — not reads.

## 4. File Manager app and share links (part D)

- Web desktop app **File Manager**: sidebar with shared folders the person
  can use and Home; list and grid views, breadcrumbs, sorting, multi-select,
  drag-and-drop upload with progress (chunked), download (folders as zip,
  streamed by hardyd), new folder, rename, move/copy (picker), delete (to
  recycle bin), properties, "Previous versions" panel per file/folder
  (restore or download an older version), quick preview for images, PDFs,
  text and video. Follows the UI rules in CLAUDE.md.
- Share links: an admin, or anyone with write access to the folder, makes a
  link to a file or folder: expiry (default 7 days, max 90), optional
  password, optional "allow uploads" (folders only), optional download limit.
  Stored in hardyd's database (token = 32 random bytes, only its hash is
  stored; password hashed like account passwords). Public page
  `/s/<token>` served by hardyd outside the desktop (no desktop session),
  minimal branded page; files are read **as the person who made the link**
  through `internal/files` and re-checked on every access (their access
  removed or account disabled = link stops). Rate limited; audited
  (created, used, revoked). "Links I've shared" in File Manager; admins see
  all and can revoke. A link page never lists hidden folders or snapshots.

## 5. SFTP and WebDAV (part E, after C)

- SFTP: OpenSSH `internal-sftp` for domain users (PAM via winbind), chrooted
  into a root-owned view `/srv/hardyos/sftp` holding bind mounts of the
  shared folders with SFTP on (permissions still enforced as the user by the
  ACLs), plus their home. Shell logins for domain users stay off.
- WebDAV: served by hardyd at `/dav/` with Basic auth over HTTPS (domain
  password checked like desktop sign-in), backed by `internal/files` as the
  person (`golang.org/x/net/webdav` FileSystem adapter).
- Per-folder switches for SFTP and WebDAV join `Services` then.
